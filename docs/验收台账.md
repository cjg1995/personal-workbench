## 大目录 Git 采集补正

清场时发现，早期联调辅助脚本的 Git 状态采集使用了 Node 默认 1 MB 缓冲。homeproject 的完整状态约 1.43 MB，homeproject-ai 约 1.34 MB，两个早期快照记录的是采集错误，因此早期“Git 状态均相同”的判断只能用于成功采集的其他 9 个目录，不能用于这两个 ERP 目录。早期证据原样保留，不补造历史状态。

辅助脚本已扩大为 64 MB，采集失败直接阻断后续联调。补采完整状态后，对两个 ERP 和四个 APP 执行了真实只读提交预览，六仓库均通过原保护检查；索引字节、store/index.js 字节和标志均未改变，11 个目录的完整前后状态一致。证据为 `.local/git-readonly-1792903488148/result.json`、`before.json`、`after.json`。没有执行 fetch、暂存、提交、推送、合并或恢复。

当前两个 ERP 分别检测到 14,379、13,257 项未跟踪文件，预览可提交项均为 0，按原规则全部不自动纳入。ERP 执行前指纹仅核对会进入提交的已跟踪/暂存内容，不读取这些不纳入提交的构建产物正文；未跟踪项仍完整列入预览。大目录列表分批显示、可搜索，避免一次创建上万个界面节点。

真实大目录的首轮审查曾因快照正文过大而超时，单份库约 243 MB。修复后保留全部文件清单，正文按单文件 512 KB、单份快照合计 16 MB 限制展示；超大工作区文件仅按大小和时间核对变化，外部查看正文。本机 14,379 项的提交预览约 3.5 秒、审查约 7.9 秒，数据库约 23 MB，200/400 项分批显示、搜索与滚动均通过，未出现渲染异常。证据为 `.local/large-repo-ui-1792904278391/result.json` 和截图，失败证据也保留。
