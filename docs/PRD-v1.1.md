## 3. 原生代码提交

### 3.1 页面和通用交互

代码提交页保留 ERP / APP 两个入口。依次呈现“选择仓库 → 检查与预览 → 执行 → 结果”；耗时操作在后台任务中心持续显示，离开页面不终止任务。

检查页显示绝对路径、当前分支、目标远端/分支、暂存及未暂存变更、未跟踪文件、排除文件及原因、已存在但未推送的提交。文件列表可搜索、定位并进入只读差异预览。提交说明为普通文本输入，不把输入拼成 Shell 命令。

执行页逐阶段显示待执行、执行中、完成、失败和未执行。正常流程不需要黑色终端输入；技术日志放在可展开区域。涉及仓库变更前，在页面明确展示实际影响的分支与文件。

结果页分别记录本地提交、远程推送、目标分支合并结果，展示提交号、实际所在分支、已完成阶段及待处理项。不把“本地提交成功、远程推送失败”合并成一个笼统成功状态。

### 3.2 ERP 功能保持

| 当前功能/规则 | 原生页面行为 |
| --- | --- |
| 可选择 homeproject 或 homeproject-ai | 仓库选择器明确区分目录，首次默认 homeproject。 |
| 只接受非空后缀的 feature-/hotfix- 开发分支 | 展示当前分支及不满足条件的原因，不暗中切到其他开发分支。 |
| 开发分支需配置 upstream；本地及远程 test 需存在，test 跟踪 origin/test | 检查结果逐项可见；失败停止，给出打开仓库处理入口。 |
| 已暂存内容与已跟踪的未暂存变更参与提交；不会自动加入未跟踪文件 | 分组预览实际提交范围。已手工暂存的新文件保留原处理逻辑；未暂存的新文件明确提示不在本次提交内。 |
| 默认说明取分支前缀之后的文字，可修改 | 提交说明预填，可编辑；默认值清晰展示。 |
| 没有可提交改动时可跳过 commit，继续 push/merge | 按钮显示“继续推送并合并”，不生成空提交。 |
| 推送开发分支 → 定位 test 工作树 → pull --ff-only origin test → merge 开发分支 → push test | 页面按同一阶段展示，不把 merge 改成 rebase/squash，不改变原分支策略。 |
| test 被其他 worktree 使用时，在该目录完成 test 操作 | 明确显示开发目录与 test 目录；有未提交的已跟踪变更时停止。 |
| 脚本可能将当前目录切到 test，不负责自动切回 | 原生流程结果明确显示最终分支；不能悄悄添加自动切回行为。 |
| 失败报告阶段与相关工作目录 | 保留实际 Git 状态，提供查看差异、打开 IDE/目录、重新检查入口。 |

首版不内置三方冲突编辑器。冲突页列出文件及当前仓库状态，用户在熟悉的工具中处理后，回到工作台重新检查；不能以“重试”为名覆盖冲突文件、强制重置或重复创建提交。

### 3.3 APP 功能保持

1. 支持易居通、项目经理、工人、司机，当前流程一次操作一个仓库；必须在 dev 分支。存在未完成 Git 操作、未解决冲突或不受支持的子模块时，展示原因并停止。
2. 获取 origin/dev。若待推送历史已经修改 store/index.js，停止并引导检查，不把本地测试城市配置推送出去。
3. 备份 store/index.js、暂存区及本次恢复信息；临时处理该文件的 Git 标记，保护其原始内容。
4. 将其余本地改动（含未跟踪文件）保存为本次自己的 stash；合并 origin/dev 后按原暂存状态恢复。仅清理本次成功恢复的 stash，不碰用户既有 stash。
5. 恢复 store/index.js 的原始内容及 assume-unchanged / skip-worktree 标记。合并、恢复或推送失败也要保留保护行为。
6. 按原脚本的纳入/排除规则形成最终提交清单；页面同时展示纳入、跳过及原因。store/index.js 始终排除；不得因富交互增加一个可绕过该保护的复选框。
7. 更新与恢复完成后，让用户核对最终清单并填写说明。取消提交仍保留已经完成的远程更新和本地恢复，界面必须清楚说明这一状态；取消不等于回滚全部过程。
8. 有实际变更才提交；没有新变更但已有未推送提交时，允许推送已有提交。推送到 origin/dev，完成后核对远程 dev 与本地 HEAD 的提交号。
9. 推送失败保留本地提交；重试先核实仓库状态，避免重复提交。stash 恢复冲突时保留 stash 标识及恢复位置，不自动反复 apply/pop。

排除规则以现有 Submit-UniApp.ps1 为迁移依据：本地配置、隐藏目录、测试目录及测试命名文件、构建产物、日志/临时文件、密钥和安装包等不自动纳入；新文件限制在既有源码目录与明确的根文件白名单内。已跟踪文件与新文件的规则不同，例如已跟踪 package.json 可纳入，新建 package.json 不会自动纳入。迁移验收必须覆盖这种差异。

## 4. 原生 APK 打包

### 4.1 页面与流程

选择 APP、Release/Debug（默认 Release）后，展示读取到的版本、包名、源码目录及 Android 工程。版本、签名和工具链沿用现有工程配置，首版不增加自动升版或改签名行为。

预检查通过后开始任务，展示四个真实阶段：编译 UniApp 资源、同步 Android 工程资源、Gradle 构建、校验 APK。只能从实际阶段判断进度；拿不到精确百分比时使用阶段状态和耗时，不编造百分比。

每个阶段提供日志查看、关键错误和日志文件位置。成功后显示 APK 路径、包名、版本、SHA256，以及资源、签名、版本三类校验结果；提供复制路径、打开文件夹和记一条工作记录。

### 4.2 必须保持的构建行为

- 使用本机 HBuilderX 的 Node/UniApp CLI、现有 Android 工程、JDK、SDK 及签名配置。
- 每次编译使用独立输出目录；AppID、包名、宿主工程映射不一致时停止。
- 校验 manifest.json、app-service.js、app-view.js 等必要输出，不能把空输出同步进宿主工程。
- 同步仅作用于对应 AppID 的 www 资源目录，保留原生工程配置；拒绝不安全的链接目录与越界路径。
- Gradle 先尝试离线构建，仅在明确属于依赖缓存缺失时联网补齐再试；编译错误不得被当作网络问题重试。
- 对导出资源、宿主资源、APK 内资源做内容校验，并验证签名、包名和版本；全部通过才标为打包成功。
- 同一 APP 的构建按顺序执行，防止并发写入同一 Android 工程和固定 APK 输出位置。不同 APP 的并行能力不是首版必要条件。
- 每次任务保留日志与对应结果；历史任务不能指向后来已被覆盖的 APK 却仍显示旧哈希。成功产物需保留任务专属副本或明确标记产物已被替换。
- 首版打包不自动安装到手机；若后续增加安装，必须单独选择设备并保持现有应用数据。

### 5.1 列表与启动过程

按 HomeProject / 推荐官分组，每行显示项目名称、工作目录、当前分支、运行状态、实际地址和最近错误。homeproject 与 homeproject-ai 必须分别显示。

主要操作：启动、停止、重新启动、打开页面、打开 IDE、打开目录、查看日志。操作能力按实际项目类型显示；小程序提供打开开发者工具，不能强行伪装成浏览器页面。

启动过程为“检查配置 → 检查既有实例/端口 → 编译或启动 → 确认可用 → 打开对应入口”。仅创建进程不代表服务已就绪。超时、进程退出、编译失败或端口被其他程序占用时，显示具体原因与实际日志。

状态至少区分：未配置、未启动、启动中、运行中、外部运行中、停止中、启动失败、状态未知。未配置和状态未知不得显示为正常运行。

### 5.3 运行管理

- 相同工作目录与启动配置只启动一个实例；点击多次不能产生多个同类服务。
- 已由 IDE 或其他工具启动的实例标为“外部运行中”。通过路径、进程身份及启动配置核实归属，不能仅凭端口就判断是同一项目。
- 首版停止操作只针对工作台自己启动并确认归属的进程及其子进程。外部实例显示打开原工具处理入口，不能按 java/node 进程名批量结束。
- 端口冲突先展示占用信息和解决入口，不自动杀进程、不静默改项目端口或配置文件。
- 重启前重新检查任务与进程身份；工作台重开后重新探测，旧 PID 不直接作为停止目标。
- 地址来自日志与运行配置的共同确认。无法取得可用地址时保留日志和启动状态，不生成猜测链接。
- 前后端依赖在项目详情中可见。首版支持逐项启动，不自动启动未选择的数据库、Redis、其他后端或远程服务。

## 6. Git 差异与人工审查（首版必做）

### 6.1 范围选择

所有已登记 Git 工作目录均可进入审查。首版提供：未暂存变更（相对暂存区）、已暂存变更（相对 HEAD）、全部本地变更（相对 HEAD，另列未跟踪文件）、两个分支/提交的版本比较，以及开发分支相对共同祖先的变更范围。

分支最终版本比较与“自分叉以来的变更”要有清楚的说明，不能混成一个含糊的“分支差异”。显示基准、目标、解析后的提交号、比较时间；远程分支引用标注最后获取状态，用户主动刷新后再比较。

改变审查范围只读取 Git 数据，不切换分支、不修改暂存区、不自动 stash，不触发提交或推送。

### 6.2 差异阅读

页面使用“文件列表 + 差异区 + 审查侧栏”。支持文件搜索、变更类型筛选、行号、上下变更跳转、并排/统一视图、展开上下文、打开文件或 IDE。

区分新增、修改、删除、重命名与未跟踪文件；文本显示实际差异，二进制文件明确提示不能作文本对比。中文路径、空格和特殊字符路径可正确打开。大文件应说明限制并提供外部查看入口，不静默省略内容。

### 6.3 人工审查记录

文件可标记“未看/已看”；问题可绑定文件及旧/新版本行位置，填写问题、预期、影响或处理建议。支持待处理、已处理待复查、已确认解决、不采纳（记录原因），并可关联一条待办。

审查记录保存仓库、范围、提交号或本地变更快照标识。工作区、暂存区或分支内容变化后，提示“代码已变化，需要复查”，不能继续把旧的已看状态当作新代码已审查。原问题保留原定位；无法定位到新行时显示位置已变化，不错误绑定到相同数字的另一行。

结束审查需人工选择“已完成/仍有待处理项”，可填写总结。空问题列表不等于代码已通过；未看文件、无法显示的文件及未解决问题都要可见。

支持保存审查记录、复制问题列表、将问题转待办、从提交页进入同一变更范围的审查。首版不自动修改代码，不设置“AI 已通过”等虚构状态，不把审查完成设为既有提交流程新增的强制门禁。

### 6.4 项目规则

HomeProject 审查提示沿用项目规则：以需求和适用业务为预期，核实完整调用链，只把可证明的新引入或明显扩大的问题列为缺陷；证据不足时写验证限制。规则入口展示本项目 AGENTS.md 与适用 .cursor/rules。

推荐官使用其自身规则；不能把 HomeProject 的 MSSQL、Java 老版本规则套用到推荐官。常规审查仍尊重 HomeProject 对 JSP 直接回显和易居通 store/index.js 本地配置的既有排除说明。

## 8. 公共任务与异常交互

长任务具有唯一记录，保存项目、类型、开始/结束时间、参数摘要、实际阶段、日志和结果位置。任务中心与具体功能页显示同一状态，切换页面不会丢失进度。

| 情况 | 交互和状态要求 |
| --- | --- |
| 等待用户输入 | 阶段显示“待确认”，保存表单，不伪装为卡住；返回对应页面后继续。 |
| 同一仓库已有写任务 | 后续提交/合并操作等待或提示冲突，审查可以阅读，但提示内容可能变化。 |
| 同一 APP 正在构建 | 不重复启动；显示现有任务并可直接进入。 |
| 开始前取消 | 不执行操作；保留已填写内容。 |
| 任务运行中请求停止 | 说明当前阶段能否停止；Git 写入阶段采用完成当前命令后停止后续步骤，不能强杀后声称已回滚。 |
| 构建停止 | 停止本任务拥有的进程，标记未完成，不把残留 APK 当成功产物；后续重新构建前重新检查资源。 |
| 某阶段失败 | 后续阶段显示“未执行”，保留此前结果；错误页提供具体对象、原因、日志位置和可执行的下一步。 |
| 应用异常退出后重开 | 重新探测进程与仓库实际状态；无法确认的任务标“已中断/待核实”，不自动重复推送、合并或构建。 |
| 外部程序已打开 | 只记录启动结果，业务成功与否需要实际结果或人工补记。 |

日志默认折叠，常用界面使用中文阶段名称。敏感值、令牌和签名口令不进入普通日志或导出内容；复制完整诊断信息前说明所含路径与日志范围。

## 10. 首页与导航（FR-01）

固定左侧导航、右侧工作区。日常：今日概览、灵感待办、工作记录、月度总结；交付：代码提交、APK 打包、TAPD 入口；开发：项目运行、代码审查；设置位于底部。任务中心在各页面都能进入。

首页保留 ERP 提交、APP 提交、APK 打包、TAPD 四个常用操作，并提供进入项目运行和人工审查的入口。点击提交/打包先进入配置和预览，不立即产生仓库写入或构建。TAPD 按已配置路径启动客户端。

快速记录明确区分“记个想法”“记一条工作”，不靠内容猜分类。记录内容是唯一必填项，项目可选；输入后可直接保存。成功后显示“已保存”及查看入口；保存失败保留输入，不能先清空再报告失败。

首页下方显示正在运行的任务、最近执行结果和最近工作记录。计数来自实际数据，首次无记录时显示空状态与录入入口。无效路径展示“需要配置”并直接进入相应设置项。

本版不展示 AI 审查、工具市场和全盘搜索等尚未交付的导航。全局命令面板及系统快捷唤起后续再设计；首版依靠应用内可见入口完成全部操作。

## 11. 灵感与待办（FR-05）

支持新增、编辑、关键词搜索、未完成/已完成筛选、标记完成和重新打开。每条保存原文、唯一 ID、创建/修改时间与完成时间；项目关联可选。首版不要求优先级、截止日期、工时或多级子任务。

列表展示正文摘要、状态、可选项目和时间；选择后在详情区编辑，离开未保存内容时明确提示。保存完成后重新打开应用仍可找到同一条记录，编辑不产生副本。

完成待办只改变状态，不自动计入工作记录或本月成果。确需记录实际结果时，由用户明确点击“记一条工作”，核对正文、结果和发生日期后另行保存；保留来源关联，重复操作可看到已有工作记录。

删除需明确选择对象并确认，不能将完成操作等同于删除。TXT 中“完成初版，未投喂大量模板”这样的句子保留原文，由用户确认是否完成；首版不做智能状态推断。

## 12. 工作记录（FR-06）

快速新增只需正文；发生日期默认当前用户的本地日期，可修改。项目、实际结果均可稍后补充，不强迫临时事项先建立待办。保存工作发生日期与系统创建/修改时间，三者各有含义。

支持编辑、删除、关键词查询、按日期/月份及项目筛选。无日期历史记录放入独立的“日期待补充”列表，补齐后才参与对应月份统计。删除或编辑不能静默改写已经保存的月报草稿。

来自提交、打包或审查的记录必须由用户明确保存。成功执行任务只证明相应技术结果，不能自动写成业务需求已交付、问题已彻底解决或产生了量化收益。记录可关联任务、提交号或审查记录，避免重复录入同一结果。

示例：当前 temp.txt 的“开关批量下单重复材料问题查找修改（未过滤过期的套餐材料）”可完整导入，但其发生日期仍待补充；不能根据 10 月 17 日的文件修改时间自动归入十月。

## 13. 月度整理与总结（FR-07）

### 13.1 素材选择与编辑

页面采用“本月素材—总结正文”的两栏布局（2026-10-29 调整：去掉右侧来源核对栏与正文条目勾选合并；姓名取设置里的默认姓名；工作成果下直接粘贴一张钉钉截图）。选择年月后，默认只列发生日期明确且属于该月的工作记录；按日期排序，可按项目筛选。无日期、其他月份和待办各有清晰边界，不自动混入成果。

用户勾选素材，选择放入模板的哪个章节，应用按确定的规则保留原文并组织成可编辑条目。可以补充结果、调整章节与顺序、合并同一事项；不调用模型改写，也不生成事实、根因或收益指标。

每个整理条目保留来源记录 ID，并可返回查看。一个条目可关联多条来源，但不能重复加入同一来源而不提示。用户也可手动补充没有对应记录的文字，标为手动补充。

正文自动保存为该月份草稿。再次选择素材时，先展示新增/变更内容，不整篇覆盖已编辑正文；源工作记录后续修改或删除时提示来源变化，保留已经编辑的草稿文本，交由用户更新。

### 13.2 现有模板

以桌面 2026年9月工作总结-陈嘉庚.docx 为模板来源，制作不含旧业务正文的空白版本。保留原有排版和固定元素，按实际文档结构组织：

1. 工作成果：主要工作、其他。
2. 个人学习和成长。
3. 个人工作计划、学习目标。
4. 部门工作中存在问题及改进建议。

当月工作记录供“工作成果”选择；学习、计划和建议由用户手动补充。待办可供写计划时参考，不能自动成为已完成成果。没有内容的章节保留空白待填，不自动编造“无”或填入九月内容。

月份、姓名和标题在导出前可见。首版只有这一份固定模板，不建设通用模板编辑器；需要复杂排版或插图时，导出后在 Word/WPS 中继续编辑。

### 13.3 导出

支持保存月报草稿、复制已整理正文、导出 UTF-8 TXT，以及导出可继续编辑的 .docx。原 PRD 的“复制/导出本月原始记录”继续保留，和“导出已编辑月报”使用不同名称，导出前明确范围。

导出使用另存为选择位置，默认文件名参考“2026年10月工作总结-陈嘉庚.docx”。已有同名文件必须确认覆盖或另存；只有文件实际写入成功才显示完成。失败保留草稿及导出设置，提供打开目录和重试入口。

AI 总结、自动评价工作影响及自动生成下月计划均不在首版范围。

## 14. TXT 导入与数据保护（FR-08）

流程：选择“灵感待办/工作记录”类型和文件 → 识别编码并预览原文 → 显示逐条划分、数量及重复项 → 保存原文件快照 → 用户确认导入 → 显示导入、跳过和失败结果。

当前两份文件按每个非空物理行一条导入。括号、顿号、逗号和句号不再拆条；原文中的标点、特殊符号及换行编码不因推断业务含义而被改写。无法识别的格式保留原文并要求先在预览中核对，不以乱码生成记录。

todo.txt 导入为未完成待办；temp.txt 导入为工作记录。两份文件都没有业务日期，系统仅记录实际导入时间，发生日期或历史创建日期标为未指定。不能使用文件修改时间替代业务发生日期，也不能自动把历史内容算入本月。

每条保存来源文件、来源行、原始文本、导入批次与导入时间。相同类型下，对已有导入原文进行逐条去重；仅统一换行符与文件开头 BOM，不随意删除正文空格。原文完全相同的条目默认跳过并在预览说明，用户可以明确选择保留另一条同文事项。手动新建记录不会因正文相同被自动删除。

如果原 TXT 一行修改后再次导入，作为新内容展示，由用户选择跳过或新增；不按行号自动覆盖工作台内已编辑的记录。重复行和新增行必须分别可见。

导入批次与记录落库应保持一致。失败时保持原文件、快照和已有数据可用；用户能知道本批是否已写入，重试仍执行去重，不能留下“也许成功”的半批结果。

首次导入后，工作台内部数据为日常录入来源。原 TXT 保留，不监听、不回写，也不自动同步记事本的后续修改；需要补导时再次手动选择文件并预览。

## 15. 设置、本地保存与备份（FR-09）

设置包含项目工作目录和显示名称、编译工具/IDE/微信开发者工具路径、TAPD 客户端路径及工作目录、月报模板和导出目录、数据及备份目录。既有 BAT 业务脚本路径不再是原生功能运行所需配置。

启动所需的环境、端口和命令来源于已登记项目及经验证的运行配置；界面提供受控字段，不能把记录正文或任意输入直接当 Shell 命令执行。原有项目文件、签名、H5 配置和本地城市配置不得被工作台静默改写。

记录、配置、执行历史、审查记录和月报草稿保存在当前 Windows 用户可写的本地数据目录。默认不需管理员权限，不在安装目录写业务数据，不上传云端。应用显示实际数据位置并提供打开目录入口。

保留云端架构中的 SQLite 本地存储候选。具体桌面宿主、数据库驱动、表结构及版本在技术预研后确定，不把建议技术栈当作用户已批准的固定实现。产品要求是普通用户可用、事务保存、重启不丢数据及可恢复备份。

提供手动备份及恢复：备份覆盖结构化记录、配置、月报草稿、审查记录和 TXT 导入快照；日志、APK、源码及项目工程仍在其各自目录，备份清单明确说明哪些只是路径引用。数据库备份必须得到一致快照，不能简单复制运行中的数据库主文件而遗漏 WAL。

恢复先预览备份日期与内容，保留当前数据副本，再明确替换范围；失败可恢复到替换前。应用更新迁移前保留备份；路径不可用或磁盘写入失败时保留未保存的输入并给出修复入口。

首版提供手动备份和导入前快照；定时自动备份频率、云端备份、任意数据目录热迁移均不增加为隐含需求。

## 16. 质量、发布与退出行为

- 平台沿用初版 Windows 10/11 x64，默认 Windows 安装包；不额外承诺便携版、云端服务或多设备同步。安装和更新保留用户数据。
- 工作台本身无需另部署后端服务器。离线可记录、查询、编辑月报和阅读本地差异；提交推送、依赖下载和 TAPD 的联网需求单独显示。
- Git、编译、导入和文件处理不会阻塞界面；真实耗时和进度按实际结果展示，不凭空承诺“一秒启动”或展示模拟成功。
- 表单、列表、差异阅读的常用操作支持键盘、可见焦点与可读错误；结果不只用红绿颜色区分。中文路径和 Windows 缩放需要实机检查。
- 保留输入和草稿；保存失败必须可见。清空数据、覆盖导出文件和恢复备份均需明确确认对象与影响。
- 关闭应用前检查运行任务，提供取消退出或按当前阶段安全结束的入口，不能无提示中断 Git 写入。长期项目服务是否继续运行应在退出界面明确列出，只操作本应用拥有的进程；重新打开后按第 5、8 节重新核实状态。
- 系统能力由受控业务动作调用，前端不获取任意命令执行、任意文件覆盖或原始凭据访问接口。Git 凭据继续使用既有受信任机制，不要求用户把口令保存到工作台普通设置。
- 不记录密钥和令牌；用户工作记录、代码、日志及月报默认均在本机。首版没有 AI 发送代码或工作材料的路径。
